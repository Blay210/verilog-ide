# H0 독립 IDE 제품 결정 기록

2026-10-08 사용자 합의. **계획이며 구현 완료를 의미하지 않는다. 현재는 구현하지 않고 함께 구체화한다.** Code-OSS 구성·배포·자체 엔진 선택은 별도 논의한다.

## 작업 공간

- 왼쪽 아이콘 바에서 Code / Simulation 두 작업 공간을 전환한다. Code는 Explorer와 소스 탭을 제공한다.
- Simulation은 Explorer 크기의 보조 사이드바 없이 중앙 Simulation 홈·파형 탭을 사용한다. 파형에 넓은 화면을 주되 기존 파형 뷰어 내부는 유지한다.
- Terminal/Output 하단 패널은 공통이다. 공간 전환으로 실행이나 내용을 종료하지 않는다.
- 각 공간의 탭·선택·커서·스크롤·배치와 파형 신호·확대·시각을 보존한다. 같은 소스 문서의 편집 내용/미저장 상태는 공간 간 공유한다.
- Testing과 Simulation의 사용자 진입은 Simulation으로 통합한다.
- Diagram은 첫 독립 앱에서 제외하되 기존 구현과 검증 근거는 보존한다. Synthesis는 후속 아이디어다.
- Chat 및 외부 extension 설치/Marketplace 지원은 제외한다. 내부 RTL 기능 구현에 extension 구조를 사용하는지는 별도 기술 설계 사항이다.

## 실행과 결과

Simulation 홈은 테스트벤치별 최신 결과를 기본으로 보여주고, 선택/펼침으로 과거 이력을 제공한다. 전체/선택/개별 실행, 취소, 로그/실패 원인과 행별 실행·파형 버튼을 제공한다.

Simulation 아이콘은 마지막 탭을 복원한다. Code에서 실행하면 소스 화면을, 홈에서 실행하면 홈을 유지한다. 완료/실패로 화면을 강제 전환하지 않고 파형 버튼으로 명시적으로 이동한다. 열린 이전 파형을 새 결과로 덮어쓰지 않는다. 같은 실행 결과의 열린 탭은 재사용하며 실행 시각/identity로 결과를 구분한다. 파형 미생성 시 이전 파형을 최신처럼 열지 않는다.

실행에 사용한 RTL/TB/package/include/설정 변경을 해당 테스트에 표시한다. 무관한 파일 변경은 구분한다. 열린 파형의 ‘소스 변경됨’과 ‘새 실행 결과 있음’은 별도 상태다. 정확한 영향 범위 판정은 구현 전 설계·검증한다.

## 이번에 명시적으로 승인한 정책

1. **미저장 코드도 실행한다.** 원본을 자동 저장하지 않고 실행 시작 시점 입력 사본을 결과와 보관한다. 실행 중 추가 편집으로 기존 결과의 입력이 바뀌면 안 된다. snapshot 일관성·identity·include/package/설정과의 대응을 설계한다. CLI는 editor buffer가 없으므로 디스크 입력과 명시적 보존 입력을 구분한다.
2. **기존 프로젝트는 최초 분류 확인 후 시작한다.** TOML이 없으면 자동 탐색 결과를 확인/수정하고 최소 TOML을 생성한다. 이후 자동 추적한다.
3. **앱 종료 시 실행 중임을 안내한다.** 종료를 선택하면 하위 빌드/시뮬레이션 프로세스까지 정리한다. 백그라운드 지속 실행은 첫 범위에 넣지 않는다. 종료 취소·미저장 문서 보호도 함께 설계한다.
4. **외부 extension 설치는 지원하지 않는다.** 사용자 명시적 결정이며 단순히 Marketplace를 숨기는 것과 구분한다.

## 가져오기 방향과 추가 설계

폴더 우클릭으로 RTL/Simulation 역할을 지정하고 아이콘 배지로 표시하는 사용자 제안을 반영한다. 탐색 결과의 드래그 분류는 역할 변경이며 실제 파일 이동과 구분한다. 기존 폴더 구조를 강제로 바꾸지 않는다.

폴더 역할과 코드 종류/실행 top은 구분한다. Simulation 폴더의 package/helper까지 모두 실행 대상으로 만들지 않는다. Package는 RTL/Simulation 양쪽에서 사용될 수 있다. 인식된 TB 파일 행의 hover 실행을 목표로 하되 여러 top의 개별 테스트 관리, 하위 폴더·파일 override, 자동 인식 복귀, 공통 source·테스트별 의존성/컴파일 순서는 다음 설계에서 확정한다. 기존 U11/U12·자동 trace 요구는 폐기하거나 구현 완료로 간주하지 않는다.

## 기술 방향과 자체 엔진 — 제안 / 미확정

Code-OSS/Electron 기반 앱, TypeScript와 기존 npm workspaces/Core/언어 서버/Verilator/파형 worker 재사용을 권장한다. 작업 공간 전환은 workbench 계층, RTL 기능은 내장 host adapter 경계를 활용하는 안이다. 현재 fork/버전/내부 extension 구성/배포 방식은 선택하거나 구현하지 않았다. 외부 확장 지원 제외는 사용자 결정이며 내장 기능의 구현 형태와 구분한다.

자체 엔진은 독립 IDE 첫 사용 흐름 안정화 이후 구현을 권장하지만 착수 날짜/언어 범위/일정은 미확정이다. 진단 일관성 설계는 전환 준비부터 고려한다. 권장 순서: 현재 진단 구분 → 독립 앱 첫 흐름 → 공통 언어 frontend 확정 → 제한된 simulator 정확성 → 성능·증분 빌드/디버깅. 사용자와 별도 합의 전 엔진 구현을 시작하지 않는다.

편집 진단과 컴파일의 언어 해석을 공유하는 것이 목표다. slang 공통 frontend + 자체 실행 backend도 후보이며 parser 전체 재작성은 확정하지 않는다. C++ 생성/직접 native 생성과 frontend 선택은 별개다. 같은 frontend라도 backend 미지원과 runtime 오류는 남으므로 언어 오류/미지원/실행 오류를 구분한다. 자체 lint 규칙의 범위, 4-state/timing/NBA/assertion·지원 SV, 증분 무효화와 속도 목표는 엔진 논의 때 정한다. C++ 경유 자체가 비효율적이라고 전제하지 않는다.

## 현재 코드 확인 — TOML / 진단 (2026-10-08)

- Core templates는 프로젝트 생성 시 TOML을 만든다. config는 TOML과 source glob을 읽는다. glob 일치 파일 검색은 폴더 역할 자동 관리나 새 TB 자동 등록과 다르다. 이번에 합의한 가져오기/분류 기반 TOML 작성·지속 갱신은 아직 미구현이다.
- semantic.ts의 documentSelector는 file Verilog/SystemVerilog다. watcher는 TOML도 감시해서 설정 변경 시 RTL을 재분석한다. SlangProvider는 manifest의 RTL/package 및 테스트별 sources, include/defines/top으로 분석한다. TOML을 SV 문법으로 검사하는 구조는 아니다.
- language-server/src/server.ts analyze catch는 manifest 부재를 제외한 분석 예외를 rtl.toml 첫 줄의 RTL diagnostic으로 게시한다. 설정 오류뿐 아니라 도구 실패/timeout도 그 위치에 표시될 수 있어 혼동의 원인이 된다. 사용자가 본 구체 오류의 원인은 메시지 없이는 확정할 수 없다.
- 개선 후보: 설정 parse/validation 오류는 설정 진단, RTL 의미 오류는 실제 소스 위치, 도구 실행/timeout은 분석 상태·Output, simulator 미지원/실패는 실행 결과에 표시한다. 실패 종류를 typed error로 구분하고 stale 진단 정리와 재시도 회귀를 검증한다. 아직 코드 수정/결함 해결을 하지 않았다.

근거 파일(분리 후 경로): vsix/packages/core/src/templates.ts, config.ts; vsix/packages/vscode/src/semantic.ts; vsix/packages/language-server/src/server.ts; vsix/packages/semantic/src/slang.ts. 읽기 확인이며 새 테스트 실행 근거가 아니다.

## 2026-10-09 추가 합의와 소스 보기 확인

- 한 TB 파일의 여러 실행 top은 하나를 선택해 기억하는 대신 각각 독립 테스트로 관리한다. 예: tb.v의 top1/top2는 tb.top1, tb.top2로 표시하고 각각 실행·결과·파형·이력·저장된 신호 구성을 구분한다. 각 실행은 해당 top만 지정한다. 파일 안의 DUT/helper module까지 모두 테스트로 등록한다는 의미는 아니며 실행 top 발견 기준은 설계해야 한다. 동일 basename의 서로 다른 파일은 경로로 구분하고 내부 identity는 파일 경로+top을 기준으로 설계한다.
- 테스트벤치 작성자가 dump/파형 파일명 코드를 직접 작성할 필요 없이 IDE가 관리한다. 원본 수정 없이 실행용 생성 입력에서 처리하는 방향이며 기존 사용자 dump 코드 중복/우선순위·VCD/FST/off·출력 격리는 기술 설계/검증이 필요하다. 이번 합의는 구현 완료가 아니다.
- 나머지 직전 추천안 수용: 새 프로젝트 만들기에서만 rtl/tb 기본 생성, 기존/빈 폴더를 열었다고 자동 생성하지 않기; 자동 TOML은 수동 설정을 존중하고 충돌 덮어쓰기 방지; 이력 수동 보존과 자동 정리 정책 마련, 한도 수치는 측정 후 결정.
- ‘파형에서 소스 확인’은 Simulation 공간을 떠나지 않고 필요할 때 파형 옆에 소스를 표시하는 제안이다. 사용자 질문에 설명하는 단계이며 상세 동작은 미확정이다. 평소에는 소스 영역을 닫아 파형 폭을 확보한다. 현재 코드(공유 editable 문서)와 실행 당시 입력(read-only)을 명확하게 구분하는 정책이 필요하며 자동 신호→소스 이동의 지원 범위도 별도 설계한다.

## 다음 설계 순서

1. 프로젝트 가져오기 → 분류 확인 → Code 편집 → 미저장 실행 → Simulation 홈 → 파형 → 재실행을 화면 흐름으로 작성한다.
2. 홈의 목록/이력/진행/실패/미생성/변경 표시와 공간 전환·공유 하단 패널을 구체화한다.
3. 공유 TOML/생성물/개인 상태의 소유권, 이력 보관 한도·보존/삭제, 재시작 복원, 종료 중 취소 실패 처리와 자동 trace 범위를 정한다.
4. 실제 host 의존성 점검 후 첫 독립 앱 구현 순서·완료 기준을 합의한다. 기술·라이선스·업데이트 조사와 성능 수치 확정은 별도 작업이다.

새 프로젝트/빈 폴더의 생성 정책은 위 합의를 따르며 실제 시작 화면, Search/Source Control의 위치는 세부 미결 사항이다. Windows 우선 기반과 중간 규모 목표(RTL 수백 파일/파형 수천 신호)를 유지한다. 깨끗한 Windows 설치 gate는 별도 환경 부재로 열려 있다. E4 완료는 지원 subset/현재 개발 환경 기준이며 전체 SV/live debugger 완료가 아니다.

이번은 문서만 변경했다. 제품 코드 변경·새 테스트/빌드·패키징/설치·앱/엔진 착수 없음. 기존 검증 근거는 [E4 수용표](e4-acceptance-summary.md)를 참조한다.
